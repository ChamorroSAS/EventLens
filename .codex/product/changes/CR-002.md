## Original request / reason

## Accepted contracts

### TC-001 → DEC-061 — Capacidad y separación

**CONFIRMED:** Beta para eventos20–200 invitados; objetivo hasta100 usuarios conectados/cargando concurrentemente, no100 procesamientos multimedia simultáneos. Un servidor de aplicación inicial; PostgreSQL separado o administrado; almacenamiento multimedia externo y procesamiento async Workers. El servidor app nunca almacena media permanentemente. API/workers/media/storage/DB/queue separables y escalables horizontalmente después sin cambiar contratos; no infraestructura distribuida masiva anticipada. EC2 conserva elección inicial del servidor app; Nginx/Docker Compose donde correspondan.

**CONFIRMED:** Subida directa navegador→storage preferida y adoptada por TC-003. Backend autoriza estado/permisos/cuotas, emite acceso temporal, registra y coordina procesamiento. Cuotas configurables:1500archivos/10GB/evento, foto25MB, video500MB/5min. No se inventa máximo de eventos concurrentes ni número workers.

### TC-002 → DEC-062 — Recuperación

**CONFIRMED:** PostgreSQL producción con PITR obligatorio; RPO≤1hora, RTO≤4horas. Backup completo diario, retención7d y pruebas periódicas de restauración; app/datos restaurados consistentes. Media independiente del backup PostgreSQL; object storage con redundancia/durabilidad y políticas de eliminación/versionado/recuperación propias según convenga. Conserva plazos de borrado/rotación confirmados; no resucitar contenido purgado tras recuperación.

### TC-003 → DEC-063 — ObjectStorage

**CONFIRMED:** Object storage compatible S3 mediante contrato proveedor-neutral evolutivo: `createUploadUrl`, `createDownloadUrl`, `completeUpload`, `abortUpload`, `exists`, `getMetadata`, `delete`, `copy`. Adaptadores posibles S3/R2/MinIO/DO Spaces, sin elección aceptada ni SDK del proveedor en lógica de negocio. Privado por defecto, sin URL permanente pública/listado público; autorización app y URLs temporales firmadas/equivalentes.

**CONFIRMED:** Carga directa navegador; confirmación verifica existencia, tamaño real, metadata, asociación evento, límites y estado inicial; después procesamiento async. Originales/derivados/exports separados lógicamente; layout físico depende del proveedor. Original intacto; adaptadores intercambiables sin cambiar reglas/permisos/lifecycle/casos de uso.

### TC-004 → DEC-064 — JobQueue

**CONFIRMED:** Cola inicial persistente PostgreSQL; Redis no obligatorio y solo justificado por métricas. Contrato evolutivo `publish`, `reserve`, `complete`, `retry`, `fail`; posibles colas futuras Redis/SQS/RabbitMQ sin selección anticipada. Web/API, Workers, Scheduler conceptualmente aislados aun si comparten infraestructura inicialmente; DB y media respetan separación de TC-001.

**CONFIRMED:** Async como mínimo foto/thumbnail/video/preview, correo, ZIP, borrado, expiración evento, limpieza, reintentos y notificaciones programadas. Obligatorio fuera del request para media/correo/exports/borrado masivo/lifecycle programado. Jobs PENDING/PROCESSING/COMPLETED/RETRYING/FAILED/DEAD; id/type/status/attempts/resource-reference/timestamps/nextRetry/lastError; sin payload grande. Hasta3 intentos automáticos; esperas configurables, backoff progresivo RECOMMENDED, ejemplos no son tiempos fijos. DEAD al agotarse; admin autorizado inspecciona/reintenta/cancela/marca no repetir con auditoría.

**CONFIRMED:** Entrega al menos una vez; idempotencia donde sea posible. Detectar PROCESSING abandonados sin jobs eternos; leases/locks/timestamps/SKIP LOCKED/heartbeats son opciones de implementación, no selección aceptada. Métricas/alertas de cola/jobs. Introducir Redis solo por evidencia de volumen/concurrencia, latencia/contención PostgreSQL, necesidad de throughput o escalabilidad; valores numéricos y umbral concreto PENDING.
